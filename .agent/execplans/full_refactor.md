# ExecPlan: Full Refactor (без изменения внешнего поведения API)

## Цели
- Упростить архитектуру и связность модулей `core/auth/blog/worker`.
- Уменьшить дублирование и количество "магических" значений.
- Нормализовать границы ответственности: роутеры, сервисные функции, хранилища.
- Усилить обработку ошибок и транзакционные границы.
- Сохранить обратную совместимость API (эндпоинты, payload, коды ответов).

## Ограничения
- Не менять `.env*`, секреты и CI credentials.
- Не добавлять новые зависимости без явного обоснования.
- Миграции БД только при критической необходимости (на текущий проход не планируются).
- Не делать коммиты/пуш.

## Baseline и стратегия
- Базовая структура и e2e-флоу уже присутствуют (auth + blog + media + worker + integration tests).
- Рефактор выполнять малыми батчами по модулям, с валидацией после каждого батча.
- В каждом батче выносить только локальные улучшения, не меняя публичные контракты API.

## Этапы

### Батч 1: `app/core`
- Упорядочить и типизировать core-утилиты (config/db/logging/constants usage).
- Устранить явные архитектурные шероховатости (например, пустые/неиспользуемые точки расширения).
- Ввести единый, предсказуемый путь инициализации инфры (без изменения поведения).

### Батч 2: `app/modules/auth`
- Свести дублирующуюся логику JWT/cookie/HTTP ошибок к небольшим helper-функциям.
- Сделать транзакционные и error-boundary в auth-роутере более явными.
- Упростить refresh-store интерфейс и внутренние адаптеры (memory/db/redis) без смены API.

### Батч 3: `app/modules/blog`
- Разделить read/write helper-логику и подготовку query-фильтров.
- Убрать повторения при чтении/валидации/ошибках.
- Сохранить текущие публичные endpoint-ы и формат ответов.

### Батч 4: `worker/*`
- Улучшить читаемость и предсказуемость конфигурации worker/celery.
- Стабилизировать интерфейс задач и минимизировать связность с web-слоем.

### Батч 5: Сквозной слой
- Привести имена/типы/docstrings к единообразию.
- Удалить dead code и мелкие smells.
- Проверить отсутствие регрессии на тестах и линтерах.

## Риски и контроль
- Риск скрытой регрессии middleware/public-path логики.
  - Контроль: отдельные middleware тесты + полный `pytest -q`.
- Риск изменения поведения JWT/cookie.
  - Контроль: auth-mvp тесты, refresh/logout тесты, сравнение кодов/деталей ошибок.
- Риск побочного влияния на DB flow.
  - Контроль: blog-flow тесты + integration marker tests.

## Критерии завершения
- Все запланированные батчи выполнены.
- После каждого батча зелёные проверки:
  - `poetry run ruff check .`
  - `poetry run ruff format --check .`
  - `poetry run pytest -q`
- Публичные API-контракты и бизнес-логика не изменены.
- Финальный отчёт содержит:
  - что и зачем отрефакторено по модулям,
  - список файлов,
  - устранённые smells/риски,
  - точные результаты валидации,
  - оставшийся техдолг P1/P2 и следующий шаг.
